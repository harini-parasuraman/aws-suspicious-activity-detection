# AWS Suspicious Activity Detection

A student-friendly project prototype for analyzing AWS CloudTrail-style events, detecting suspicious patterns with simple rules and an Isolation Forest model, and preparing security findings for notification.

> **Current status:** The included version is a **local prototype**. It runs on sample JSON data and does not require an AWS account. It does not claim to detect real attacks. AWS deployment steps are documented separately and should only be done after reviewing cost and permissions.

## Project modules

1. **Data Engineering** — parse CloudTrail JSON, normalize events, and build time-window/identity activity features.
2. **Cloud Engineering** — planned AWS integration: CloudTrail → S3 → Glue/Athena, with EventBridge → Lambda → SNS for event-driven notifications.
3. **AI Engineering** — Isolation Forest anomaly scoring over aggregated activity features.
4. **Security Engineering** — transparent detection rules, safe notification handler, least-privilege and incident-response guidance.

## Architecture

```text
AWS account events
       |
   CloudTrail --------------------> GuardDuty findings
       |                                   |
       v                                   v
   Amazon S3                         EventBridge rule
       |                                   |
 Glue / Athena (optional)                  v
       |                               Lambda -> SNS email
       v
Processed event features
       |
Python rules + Isolation Forest
       |
Security findings / review
```

The local prototype starts at a sample CloudTrail JSON file and runs the processing, rules, and AI steps locally. The AWS path is a future deployment path and is **not automatically provisioned by this repository**.

## Requirements

- Python 3.10 or newer recommended

- A GitHub account
- AWS account only for the optional deployment stage

## 1. Run locally first (no AWS account required)

### Windows PowerShell

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
python run_pipeline.py --input data/sample_cloudtrail.json --output-dir outputs
python -m unittest discover -s tests -v
```

If PowerShell blocks activation, use `.\.venv\Scripts\python.exe` instead of activating the environment.

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
python run_pipeline.py --input data/sample_cloudtrail.json --output-dir outputs
python -m unittest discover -s tests -v
```

The pipeline writes:
- `outputs/normalized_events.csv`
- `outputs/activity_features.csv`
- `outputs/rule_findings.json`
- `outputs/anomaly_results.csv`

These files are generated locally and are ignored by Git by default.

## 2. Understand the outputs

- **Normalized events:** one row per input event, with common fields extracted.
- **Activity features:** counts grouped by identity and time window.
- **Rule findings:** explainable findings generated by simple configurable rules.
- **Anomaly results:** Isolation Forest prediction and score. An anomaly is a review signal, not proof of an attack.

The sample dataset is synthetic and is included only for development/testing. Do not present its output as evidence of a real incident or model performance in production.

## 5. Next AWS deployment stage

After the local tests pass:
1. Create/secure your AWS account and enable MFA.
2. Set a billing budget before enabling paid services.
3. Choose a Region and create an encrypted, private S3 log bucket.
4. Configure CloudTrail to deliver management events to S3.
5. Enable GuardDuty only after reviewing current pricing and data sources.
6. Configure EventBridge → Lambda → SNS using least-privilege roles.
7. Test using supported sample findings and controlled test events.
8. Capture your own console screenshots and document what was actually deployed.

AWS prices and free-tier terms change. Check the current AWS pricing pages before deployment. Never use production resources for experiments.

## Security notes

- Never commit AWS access keys, credentials, `.env` files, private logs, or real customer data.
- Keep S3 Block Public Access enabled.
- Use least-privilege IAM policies and MFA.
- The included Lambda handler only publishes a notification; it does not disable users or modify resources.
- Review all AWS permissions and costs before deploying.
